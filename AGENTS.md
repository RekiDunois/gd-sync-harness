# AGENT.md

This repository may be published publicly. Treat every tracked file, commit message, branch name, tag name, PR title/body, issue, test fixture, generated artifact, and example as potentially public.

## Public-by-default rule

Before creating any commit, assume the entire commit and its metadata will be permanently visible on the public internet.

Do not commit information copied from the local machine or a real deployment unless it is intentionally public and necessary for the project.

If there is any doubt whether a value is environment-specific, personal, private, credential-like, or identifying, replace it with a clearly synthetic example or stop before committing.

## Never commit these values

Do not include any real value from the following categories in tracked content or commit metadata:

- OAuth client IDs, client secrets, refresh/access tokens, API keys, passwords, cookies, private keys, certificates, service-account credentials, or credential files.
- Real rclone remote names or aliases.
- Real Google account names, email addresses, account labels, Drive IDs, folder IDs, profile UUIDs, or other deployment identifiers.
- Real local usernames, home-directory names, hostnames, device names, IP addresses, SSH hosts, mounted-volume names, or absolute paths from the developer machine.
- Real knowledge-base, vault, workspace, project, customer, organization, or private folder names unless they are intentionally public project terminology.
- Real quota/capacity values, usage figures, account topology, or operational details copied from a live environment.
- Real filenames or excerpts from private notes, documents, logs, databases, configuration files, incident artifacts, or test data.
- Internal incident details that reveal how a specific local environment is configured. Describe the technical bug generically instead.

This restriction applies equally to:

- source code and comments;
- Markdown and documentation;
- examples and sample output;
- tests and fixtures;
- log snippets and error messages;
- commit subject and body;
- branch and tag names;
- PR/issue text generated by an agent.

## Safe example vocabulary

When an example needs a concrete value, prefer obviously synthetic placeholders such as:

```text
example-drive-primary
example-drive-secondary
notes-main
research
~/ExampleVault/Main
~/ExampleData/Research
/ABSOLUTE/PATH/TO/EXAMPLE-VAULT
Knowledge Mirror/Notes
Knowledge Mirror/Research
example@example.invalid
<profile_uuid>
<folder_id>
<remote>
<remote-path>
```

Do not derive example names from the current local configuration. Do not make a real value "slightly different"; use a clearly generic placeholder instead.

## Commit-message rules

Commit messages must describe the code change, not the developer's private environment or the history of a local incident.

Good:

```text
Fix remote path construction
Apply structured filters during initial copy
Persist executable paths for launchd jobs
Add repository contribution guardrails
```

Avoid messages that mention:

- the name of a live remote/account/profile;
- a real local path or folder name;
- what happened to a particular developer's machine;
- where a backup or recovered file came from;
- validation against a specifically named personal account;
- private data that happened to expose the bug.

A useful commit body should explain the technical cause, behavior, and fix using generic terminology.

## Documentation rules

Documentation must be reproducible without depending on one developer's setup.

- Mark example configurations as illustrative when that is not already obvious.
- Use generic account labels such as `Account A` and `Account B`.
- Use generic remotes such as `example-drive-primary`.
- Use synthetic paths and folder names.
- Never paste output from a live credential/configuration command directly into documentation.
- Never paste a real `rclone.conf`, OAuth JSON file, SQLite row, launchd plist, environment dump, or log file.
- If command output is useful, construct a minimal synthetic example containing only fields needed to explain the behavior.

## Tests and fixtures

Test data must be synthetic.

- Use `t.TempDir()` or equivalent temporary paths where possible.
- Use generic usernames such as `user` or `x` if a path shape must be tested.
- Use generated/random test UUIDs rather than copied production identifiers.
- Do not copy real notes, filenames, directory layouts, logs, configuration fragments, or remote listings into fixtures.
- A regression test should encode the bug's invariant, not the private data that originally triggered it.

## Sensitive files

The repository `.gitignore` is only a safety net. Never rely on it as permission to place secrets in the working tree.

Pay particular attention to files such as:

```text
.env
.env.*
rclone.conf
credentials.json
token.json
client_secret_*.json
*service-account*.json
*.pem
*.key
*.p12
*.sqlite
*.log
```

If a sensitive file is already tracked, `.gitignore` will not protect it. Stop and remove it from Git history before publishing.

## Mandatory pre-commit review

Before every commit, the agent must review the staged diff and the proposed commit message.

At minimum run:

```bash
git diff --cached --check
git diff --cached --stat
git diff --cached
```

Then inspect staged text for common credential/private-data indicators. A reasonable local check is:

```bash
git diff --cached -U0 | grep -Ein \
  'client[_-]?secret|refresh[_-]?token|access[_-]?token|api[_-]?key|password|BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY|/Users/|/home/|@gmail\.com|@icloud\.com' \
  && { echo 'Review possible sensitive staged content before committing.'; exit 1; } \
  || true
```

This pattern is intentionally incomplete and may produce false positives. Passing it does not prove that the commit is safe.

The agent must also manually check for environment-specific names that cannot be detected reliably by regex, especially remote names, folder names, profile names, account labels, and incident descriptions.

## Pre-commit decision rule

Before committing, answer all of these questions:

1. Could any string in the staged diff identify a real person, account, machine, private folder, or deployment?
2. Did any example value originate from local configuration, command output, logs, or a real cloud account?
3. Does the commit message reveal more about the developer's environment than is required to understand the code change?
4. Are credentials, tokens, IDs, or private artifacts present even if they look expired or harmless?
5. Would the commit still make sense if every example were replaced with an obviously synthetic value?

If any answer is concerning or uncertain, do not commit. Sanitize first.

## Existing-history rule

Do not assume that deleting or editing a value in a later commit removes it from Git history.

If sensitive or identifying information was already committed:

- stop creating additional cleanup commits merely to hide it;
- determine whether history rewriting is required;
- rewrite affected commit content/messages and update all relevant refs before publication;
- rotate any exposed credential even if history is rewritten;
- prefer a clean orphan/squashed public history or a new public repository when a strict separation from private history is required.

## Agent behavior

When asked to commit changes:

1. Inspect `git status` and the staged diff first.
2. Do not automatically stage unrelated files.
3. Do not copy values from local config into code, tests, docs, or commit messages.
4. Sanitize examples before staging them.
5. Keep commit messages technical and environment-neutral.
6. If the repository may be public and safety is uncertain, stop before the commit and report the questionable value/category without reproducing secrets.
7. Never "fix it in the next commit" when the problem can be prevented before the current commit.

## Parallel Development

When multiple agents work on this repository, use Git worktrees instead of
sharing one working directory.

- Store secondary worktrees in a sibling `worktrees/` directory next to the primary checkout, using one directory per agent or branch. Interpret this location relative to the primary checkout, not the current worktree.
- Each agent must operate from its own worktree directory.
- Keep each worktree on its own branch; do not switch branches in another agent's worktree.
- Before removing a worktree, confirm that its changes have been committed or intentionally discarded.

These rules take precedence over convenience and over preserving incidental local details in debugging narratives.
